# ペルソナとアプローチの検討

検討結果は `docs/persona.md` にまとめる。すでにあるときは、新しい情報を足して更新する。作り直さない。

## 1. 今の状態を読む

- `docs/persona.md`（あれば）、`docs/mold-model.md`、`AGENTS.md` を読む。
- `AGENTS.md` の前提を崩さない：サーバーはない、ESP32 は計測と記録だけ、カビリスクの判定はアプリ側。
- 引数やユーザーの発言から、今回の新しい情報が何かを決める。新しい情報（実体験、ヒアリング、実測、競合）がない場合は、何を検討したいかを1つだけ聞く。

## 2. 足りない情報を聞く

推測で埋めずに、足りない分だけユーザーに聞く。実体験やヒアリングは、次の3つに分けて聞く。

- **場所**：どこにカビが生えたか（例：天井の水漏れ部分、風呂場のプラスチック製の棚）
- **原因**：本人が原因だと思ったこと。「分からない」も記録する
- **対策**：そのときやったこと、やろうと思ってやらなかったこと（「面倒で貼り直していない」など）

## 3. まとめる

`docs/persona.md` は次の節で構成する。すでにある節は、その中に追記する。

| 節 | 書くこと |
| --- | --- |
| 結論 | メインのペルソナ、方向性、キャラの扱いを箇条書きで。冒頭の1文で答えを言う |
| 競合との比較と新規性 | 既存の自動制御（SwitchBot、Nature Remo など）とこのプロダクトの比較表 |
| ペルソナ | B（メイン）・A（補助）・C（補助）の表。行は人物像、カビへの意識、今やっている対策、欲しいもの、このペルソナの役割 |
| 実体験のヒアリング | 表の列は「場所・考えられる原因・そのときの対策・センサーで分かるか・アプリでできること」。表の下に「分かったこと」 |
| 想定シミュレーション | 生活シナリオごとの表。列は「シナリオ・湿気の出どころ（目安）・部屋の中央のセンサーの見え方・センサーだけでは気づけないこと・提案する行動」。表の下に「分かったこと」 |
| するべきでないこと | 列は「やらないこと・判断したペルソナ・理由」。A と C から見て離れる理由がある機能を挙げる |
| キャラの位置づけ | キャラを何のために使うか |
| 次にやること | `- [ ]` のチェックリスト。確かめる方法が分かる粒度で書く |

### ペルソナの使い方

- 機能は B に合わせて決める。
- A は「手間と継続」、C は「正確さと信頼」のハードルを測るために使い、主に「するべきでないこと」を判断する。
- ペルソナを足したり入れ替えたりするときは、理由を結論に書く。

### 実体験の整理で必ず分けること

- **センサーで分かるもの**（入浴などで湿度が急に上がる、換気後に下がるまでの時間、高湿度の継続時間）と、**分からないもの**（定期的な手入れ、水漏れ、表面にカビが生えているかどうか）を分ける。分からないものはリマインドなどで補う案にし、検知できるとは書かない。
- 原因が「知らなかった」のか「知っていたがやらなかった」のかを分ける。後者なら、促すタイミングと手間の減らし方を考える。

### シミュレーションの計算

数値は計算上の目安として書き、「実測ではない」と明記する。計算の前提（部屋の広さ、室温、外気温）も書く。

```
飽和水蒸気圧 es(T) = 6.112 · exp(17.62·T / (243.12 + T))   [hPa]（mold-model.md と同じ Magnus 式）
露点 Td: γ = ln(RH/100) + 17.62·T / (243.12 + T),  Td = 243.12·γ / (17.62 − γ)
飽和水蒸気量（目安）: 10℃ 9.4 g/m³, 15℃ 12.8 g/m³, 20℃ 17.3 g/m³, 25℃ 23.0 g/m³, 30℃ 30.4 g/m³
部屋の水蒸気量 [g] = 飽和水蒸気量 × RH/100 × 部屋の体積 [m³]   （1K の洋室7畳で約28m³）
```

- 冷たい表面（窓、外壁側の壁、押し入れ）の湿度は、`docs/mold-model.md` の ΔT の考え方で推定する。
- カビの目安として「湿度70%以上で生えやすく、80%以上で急に増える」を使う場合は、一般的な目安と書く。リスクの計算そのものは `docs/mold-model.md` に従う。
- 1日の推移のように時間で変わる値は、Mermaid の `xychart-beta` の折れ線グラフで示す。目安の線は2本目の線で描き、出来事はグラフの下に1行で書く。

## 4. 書き方

- `docs/` の他のファイルに合わせ、である調、短い文で書く。1文目でその節の結論を言う。
- 断定できないことは「未確認：」で始め、確かめる方法を書く。同じ内容を「次にやること」にも入れる。
- 健康への影響や医療的な効果は書かない。カビについては「生えている」ではなく「生えやすい状態」と書く。
- 書き終えたら、変えた節と、新しく増えた「するべきでないこと」をチャットで短く伝える。機能案のチェックは `persona-review` スキルで行えることも伝える。
