# ペルソナレビュー

`docs/persona.md` を基準に、対象が「メインのペルソナ B の役に立つか」と「A・C から見てやるべきでないことに当たらないか」を判定する。判定の根拠は `docs/persona.md` の記述だけにし、自分の好みで基準を足さない。

## 1. 基準を読む

1. `docs/persona.md` を全部読む。ない場合はレビューせず、`persona-study` スキルで先に作るよう伝えて終わる。
2. リスクの計算や表示に関わる対象なら、`docs/mold-model.md` も読む。

## 2. 対象を決める

- 引数が文章なら、その機能案を対象にする。
- 引数がファイルパスならそのファイル、PR 番号なら `gh pr diff <番号>` を対象にする。
- 引数がなければ `git diff main...HEAD` と未コミットの差分を対象にする。差分もなければ、何をレビューするかユーザーに聞く。
- コードの差分は、ユーザーから見える振る舞い（画面、通知、文言、入力の手間、提案する行動）に読み替えてから判定する。内部のリファクタリングだけなら「ペルソナへの影響なし」と書いて終わる。

## 3. 判定する

次の観点を順に確かめる。`docs/persona.md` の表の内容が変わっていたら、その時点の内容に従う。

1. **B の役に立つか**：B の「欲しいもの」（自分の家で、どこで何をすればいいかが1行で分かる／効いたかどうかが分かる）に近づくか。
2. **A のハードル（手間と継続）**：手入力の回数、通知の頻度、メイン画面に数値やグラフを出していないか。
3. **C のハードル（正確さと信頼）**：健康・医療の表現、「カビが生えている」という断定、センサーで分からないことを分かるように言っていないか。
4. **「するべきでないこと」の各行**：表の各行に当たるかを1行ずつ確かめる。
5. **センサーで分かる範囲**：`docs/persona.md` の「センサーで分かるか」の区別を超えた判定や通知をしていないか（水漏れの診断、表面の状態の断定など）。
6. **競合と同じ土俵か**：家電の自動制御など、既存サービスがすでにやっていることに寄っていないか。

判断できない点は「未確認」とし、何を確かめれば判断できるかを書く。

## 4. 出力

チャットに次の形で返す。

```
## ペルソナレビュー：<対象の短い名前>

判定：進める / 直して進める / やめる
<判定の理由を1〜2文>

| 観点 | 結果 | 根拠（docs/persona.md の該当箇所） |
| --- | --- | --- |
| B の役に立つか | ○ / △ / × | ... |
| A：手間と継続 | ... | ... |
| C：正確さと信頼 | ... | ... |
| するべきでないこと | 該当なし / 「<行の名前>」に該当 | ... |
| センサーで分かる範囲 | ... | ... |
| 競合と同じ土俵か | ... | ... |

### 直すとよい点
- <具体的な直し方。文言なら言い換え案も出す>

### 未確認
- <確かめる方法>
```

## 守ること

- `docs/persona.md` はレビュー中に書き換えない。レビューから新しい「するべきでないこと」や「次にやること」が見つかったら、追記案として出力の最後に書き、追記するかどうかはユーザーに任せる。
- 文章は `docs/` の他のファイルに合わせ、短い文、である調で書く。
