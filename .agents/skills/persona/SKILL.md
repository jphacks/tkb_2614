# ペルソナを使った検討

`docs/persona.md` を材料に、人が決めるための情報を短く出す。決めるのはチームで、このスキルは機能を止めたり消したりする判定をしない。ペルソナはプロジェクトの途中で決めたものなので、今ある機能はペルソナに合わせて当てはめる対象であり、否定する対象ではない。

最初に `docs/persona.md` を読む。ない場合は「更新」として作るかどうかをユーザーに聞く。

引数で何をするかを決める。引数がなければ「当てはめ」を行う。

## 当てはめ（デモ・発表・優先順位を決める前）

1. 今ある機能を洗い出す。`docs/app-foundation.md`、`docs/ble-protocol.md`、`docs/mold-model.md` を読み、足りなければ `app/` と `firmware/` を見る。
2. 各機能を、ペルソナ B の場面（`docs/persona.md` の実体験とシミュレーションのシナリオ）に当てはめる。どの場面にも当てはまらない機能は「デモでは脇役」とだけ書き、消す提案はしない。
3. 出力：

```
## 今ある機能の当てはめ

| 機能 | 効く場面（ペルソナ B） | デモ・発表での扱い |
| --- | --- | --- |
| ... | ... | 主役 / 補足 / 脇役 |

デモの流れの案：<場面の順に3〜5ステップ>

足すと一番効くもの（最大3つ）：
- <機能>：<効く場面>。<ハッカソンの残り時間で作れる大きさか>

表現で直す箇所：
- <ファイル:行>「今の文言」→「言い換え案」
```

「表現で直す箇所」は、`docs/persona.md` の「表現で避けること」に当たる文言だけを挙げる。

## 案（新しい機能を1つ足すか迷ったとき）

機能案を1つ受け取り、5行以内で返す。

- 効く場面：ペルソナ B のどの場面か。なければ「当てはまる場面なし」
- 気をつける点：「これから足す機能で避けること」に近ければ、その行と代わりの案
- 表現：「表現で避けること」に当たる言い回しがあれば言い換え案
- 大きさ：今のコードから見た作業量の目安

足すかどうかの結論は書かない。

## 更新（ヒアリング・実測・競合調査などで新しい情報が入ったとき）

新しい情報を `docs/persona.md` に足す。作り直さず、該当する節に追記する。

- 実体験やヒアリングは「場所・原因・対策」に分けて聞き、足りない分だけユーザーに聞く。表の列は既存の「実体験のヒアリング」の表に合わせ、「センサーで分かるか」で、検知できるものとできないものを分ける。
- シミュレーションの数値は計算上の目安として書き、「実測ではない」と明記する。露点や表面の湿度は `docs/mold-model.md` と同じ Magnus 式で計算する（`es(T) = 6.112 · exp(17.62·T / (243.12 + T))`）。時間で変わる値は Mermaid の `xychart-beta` で示す。
- 新しく「表現で避けること」「これから足す機能で避けること」に足す行があれば、追記する前にユーザーに確認する。
- 終わったら、変えた節を1〜2行で伝える。

## 書き方

- `docs/` の他のファイルに合わせ、である調、短い文で書く。
- 判断できないことは「未確認：」で始め、確かめる方法を書く。
