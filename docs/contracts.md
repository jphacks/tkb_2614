# アプリ内のデータ契約（暫定）

この文書はアプリ内の境界をそろえるための契約。ハードウェアとの通信方式・wire payload・BLE UUIDを決めるものではない。現在はモックのみを使用する。ルートのAGENTS.mdにあるBLE read / pollingは従来の設計案として扱い、ハード側と合意する際に再確認する。

型の定義は `app/src/domain/measurement.ts` と `app/src/domain/prediction.ts`。契約を変更するときはコード・この文書・テストを同時に更新する。

## 計測値: Measurement

| フィールド | 型・単位 | 意味 |
| --- | --- | --- |
| `deviceId` | 空白だけではない文字列 | アプリ内のデバイス識別子。BLEアドレスと同一とは限らない |
| `temperatureC` | 有限のnumber、°C | 温度。文字列・NaN・Infinityは不可。機種固有の測定範囲はまだ設けない |
| `relativeHumidityPercent` | 有限のnumber、0〜100 % | 相対湿度。0〜1への正規化はしない |
| `measuredAt` | UTC日時の文字列、またはnull | センサーでの計測時刻。不明・時計未同期ならnull。受信時刻で埋めない |
| `receivedAt` | UTC日時の文字列 | 取得元のアダプターがアプリで値を受け取った時刻。端末の時計を使う |

日時は `Date#toISOString()` の形式（例: `2026-10-24T03:00:00.000Z`）。内部ではUTCで保持し、画面で端末のタイムゾーンに変換する。デバイスと端末の時計の大小関係は検証しない。

```json
{
  "deviceId": "mock-room-01",
  "temperatureC": 24.2,
  "relativeHumidityPercent": 55,
  "measuredAt": "2026-10-24T03:00:00.000Z",
  "receivedAt": "2026-10-24T03:00:00.300Z"
}
```

`parseMeasurement(unknown)` で取得値を検証し、必要なフィールドをコピーする。不正なデータは履歴・予測へ渡さず、取得エラーとして扱う。通信上の単位や時刻表現が異なる場合、アダプターがこの形式へ変換する。

## 取得元: MeasurementSource

```ts
interface MeasurementSource {
  readonly label: string;
  readLatest(signal: AbortSignal): Promise<Measurement>;
}
```

- `label` は取得元の表示名。画面は具体的なモック/BLEクラスを参照しない。
- 1回の呼び出しは1台の最新値1件を返す。現在の画面は1台用で、複数台の集計は未定。
- `receivedAt` はread完了時の受信時刻を設定する。キャッシュを返すアダプターでは、毎回現在時刻に書き換えず、そのデータを実際に受信した時刻を保持する。
- 失敗はPromiseのrejectで通知する。画面に表示できるErrorメッセージにする。呼び出しが永久に待機しないよう、実通信アダプターでタイムアウトを設ける。
- `signal` の中断時はタイマー・通信待機・購読などのリソースを解放して終了する。中断後の結果は呼び出し側でも無視する。
- 現在の収集処理は開始直後に1回取得し、成功・失敗の完了から5秒後に再取得する。これはモック用のアプリ内スケジュールで、ハード側の送信間隔を規定しない。
- 失敗しても直前の成功値と履歴を保持し、自動再試行する。新たな成功でエラー表示を解除する。起動直後に失敗した場合は履歴0件のまま。
- アプリが非アクティブになった時、画面が破棄された時、手動再取得時に現在の取得を中断する。復帰・手動再取得では直ちに再開する。1つの収集処理内ではreadを重ねない。

このreadインターフェースはアプリ側の暫定契約。ハード側でpush方式になった場合、購読結果を保持するアダプターなどで吸収するか、必要に応じてこの契約を改訂する。まだ実通信アダプターはない。

## 履歴

- 成功した取得値を受信順の逆順（最新取得が先頭）で最大30件、メモリに保持する。
- 取得履歴であり、センサーのユニークな計測イベント一覧ではない。同じ計測値の再取得も追加され、重複除去・計測時刻による並べ替えはしない。
- アプリ終了・画面の再マウントで消える。非アクティブ中は保持するが、データ収集はしない。永続化・バックグラウンド収集は未実装。

## 予測: MoldPredictor / MoldPrediction

```ts
interface MoldPredictor {
  predict(
    measurements: readonly Measurement[], // 最新取得順。変更しないこと
    signal: AbortSignal,
  ): Promise<MoldPrediction | null>;
}
```

| 戻り値のフィールド | 型 | 意味 |
| --- | --- | --- |
| `riskLevel` | `'low' \| 'medium' \| 'high'` | 予測リスクの表示区分。区分の判定基準は未定 |
| `horizonHours` | 正のnumber | 何時間後を対象とするか |
| `generatedAt` | UTC日時の文字列 | 予測の作成時刻 |
| `basedOnReceivedAt` | UTC日時の文字列 | 使用した最新計測値の受信時刻 |
| `isPlaceholder` | boolean | 仮実装の結果かどうか。trueなら画面でも明示する |

- データ不足は `null`、処理の失敗はreject。計測値の取得と予測の失敗は別に扱う。予測に失敗しても計測値・履歴の表示と収集を続ける。
- 新しい計測値が入るたびに予測を依頼する。前の予測は中断し、遅れて届いた古い結果で上書きしない。
- 予測は最新の成功した取得値に基づく。計測値の取得に失敗している間は前回の予測が残り、元データ受信時刻で鮮度を確認できる。
- 非同期のモデル・APIへ置き換えられるようPromiseにしている。実装側はsignalに応じて処理を中断し、上記の形に整えた結果を返す。
- 現在の `placeholderMoldPredictor` はデータがあれば「24時間後・中リスク」を常に返すだけ。温湿度からの判定も実際の予測も行っていない。判定閾値・モデル・予測期間・必要な履歴量は後で決める。

## ハード側と後で合意する項目

- BLE等の通信方式、read / notify等の取得方式、UUIDと接続・切断・再接続手順。
- payloadの形式、文字コード、byte order、単位、欠測・エラー表現、バージョン管理。
- デバイス識別子、複数台の扱い、計測間隔・取得間隔。
- NTP同期前後の時刻の意味と表現、時計のずれ、タイムゾーンの扱い。
- 不揮発メモリに蓄積した履歴の転送、バッチ・ページング・重複除去に必要なID。
- タイムアウト、センサー故障、権限拒否、接続喪失からの復帰。

実通信の契約を確定・変更するときは、この文書に追記し、アプリとファームウェアの対応変更を同じコミットに含める。
